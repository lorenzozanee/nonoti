# nonoti v0.1.0 Design

## Goal and release boundary

nonoti batches eligible Android notifications during a user-defined Focus session and returns control after the session through a quiet release. The app is local-only, requests no network permission, and supports Android 13 and newer only on device, ROM, and OS combinations that pass the compatibility self-test.

The product specification sections 12 through 18 override earlier simplified descriptions. A successful build is not enough for release: the Technical Spike gates the full product. A device that cannot prove the required behavior is shown as unsupported and cannot start Focus.

## Delivery sequence

1. Build the smallest end-to-end Technical Spike: permissions, an app-owned Automatic Zen Rule, one-shot Focus, notification capture and deduplication, snooze, quiet release, recovery, and compatibility evidence.
2. Only after the Spike passes on the supported matrix, add recurring schedules, the full Box, Settings, Emergency Access, and polished adaptive UI.
3. Keep unsupported combinations blocked. Do not add degraded best-effort Focus behavior.

## Architecture

Use one `app` module with feature-first packages and unidirectional data flow:

```text
Compose UI -> ViewModel (StateFlow) -> Repository -> Room/DataStore/platform services
```

- `focus/`: schedule validation, continuous-session calculation, Focus state, countdown, and screens.
- `box/`: captured notification snapshots, aggregation, retention, source-app opening, and screens.
- `settings/`: permission readiness, call/alarm policy, allowed apps, retention, privacy, and screens.
- `notifications/`: listener, eligibility policy, snooze coordination, Zen rule, alarms, release, recovery, and summary notification.
- `data/`: Room database, entities, DAOs, DataStore settings, and repository implementations.
- `core/`: time abstraction, immutable domain models, navigation destinations, and narrowly shared UI primitives.

Compose code renders immutable state and emits events. It never calls Room, DataStore, NotificationManager, AlarmManager, PackageManager, or NotificationListenerService directly.

Use Hilt for Android dependency injection because platform services and deterministic fakes are required across runtime and instrumented tests. Use `java.time` APIs available at the minimum SDK. Keep time, alarms, notification policy, installed apps, and device identity behind focused interfaces.

## Persistent model

Room stores:

- `FocusBlock`: id, start minute, end minute, enabled state.
- `FocusSession`: id, start/end instant, origin, state, failure reason, boundary token, release state, summary state.
- `CapturedNotification`: session id, system key, package, channel, conversation id, text fields, timestamps, active state, group metadata, and source-app fallback metadata.
- `CompatibilityResult`: device fingerprint fields, OS version, app version, completed checks, result, and timestamp.

DataStore stores call/alarm policy, retention choice, allowed package names, onboarding state, and last recovery outcome. PendingIntent values are memory-only and are never written to Room.

Room and DataStore are excluded from cloud backup and device-to-device transfer.

## Focus and schedule rules

`FocusState` has `Idle`, `Focusing`, `Releasing`, and `Unsupported`. State is persisted but always reconciled against current time, permissions, compatibility result, and the actual app-owned Zen rule.

Daily blocks use minute precision and half-open intervals. Validation rejects equal endpoints, durations below five minutes, durations of 24 hours, overlaps, and adjacency on a circular 24-hour timeline. Cross-midnight blocks are split into normalized intervals only for comparison.

Start now creates no recurring block. An end time not after the current local time means the next day. During Focus it may only extend the current continuous session. Planned and one-shot spans that overlap or touch merge at runtime without an intermediate release.

Every boundary operation carries a stable session id and boundary token. Duplicate alarms, service reconnects, broadcasts, and recovery passes become no-ops after the intended transition has already completed.

Time, timezone, boot, package replacement, and exact-alarm permission events trigger reconciliation. DST gaps move to the next valid local time; repeated local times execute a boundary once. A late wake starts Focus only if the current time is still inside a valid span.

## Permissions and fail-open behavior

Focus requires:

- Notification Access.
- Notification Policy Access and a verified app-owned Automatic Zen Rule.
- Exact alarm capability where the OS requires it.
- Post Notifications permission and an enabled summary channel.
- A passing compatibility result for the current device, ROM, and OS version.

Missing readiness disables scheduled and one-shot Focus. If readiness is lost while active, capture and snooze stop, the app removes its Zen rule as soon as possible, the session becomes `Unsupported`, and the next foreground entry runs recovery. The app never repeatedly fights a user's manual Zen rule change.

## Notification capture

The listener processes callbacks quickly and moves database work to an application coroutine scope. It ignores nonoti itself, work-profile notifications, group summaries when child notifications exist, non-clearable or ongoing notifications, foreground services, calls, alarms, media, navigation, system safety and emergency notifications, allowed apps, and notifications that cannot be safely snoozed.

For an eligible post during `Focusing`:

1. Upsert by `(sessionId, systemNotificationKey)`.
2. Keep the original capture time and update mutable text and active state.
3. Retain a memory-only content intent when available.
4. Snooze no later than the current continuous-session end.

Repeated updates do not increase the distinct-message count. Source cancellation keeps the local snapshot and marks it inactive. Group summaries are stored only when no usable child notification is available.

## Quiet release

At the final continuous-session boundary:

1. Atomically move the session to `Releasing` while keeping the Zen rule active.
2. Wait for snoozed notifications to return, bounded by a short fixed timeout.
3. Record recovered and missing notification counts.
4. Remove the app-owned Zen rule even when recovery is incomplete.
5. Send one summary notification using an idempotent persisted summary token.
6. Finish in `Idle` after success, or `Unsupported` with a clear recovery message after an abnormal release.

The app never recreates third-party notifications. Compatibility self-test includes user confirmation that the restore was silent and only the nonoti summary alerted.

## UI structure

Use a flat Material 3 interface. Compact widths use a bottom navigation bar; medium and expanded widths use a navigation rail. Avoid decorative imagery, gradients, nested cards, and oversized text. Existing launcher artwork is sufficient for branding.

### Focus

- Readiness state shows each required capability and its system-settings action.
- Idle state shows daily blocks, a plus action, and Start now.
- Active state shows only end time, remaining time, recovery status, early-end confirmation, and the low-emphasis emergency long-press entry.
- Releasing state shows quiet restoration progress and no Box content.
- Unsupported state explains the failed capability and offers recovery or self-test.
- The block sheet shows start, end, duration, cross-midnight status, and validation errors.

### Box

Outside Focus, show a dense list grouped by app with app icon, app name, title, body, relative time, distinct count, and inactive-source state. A tap uses a valid memory-held content intent, otherwise opens the source app home, and preserves the snapshot on failure.

During Focus, the Box destination renders a locked state without querying or composing notification content. Emergency Access requires a static launcher shortcut or long-press fallback, a confirmation, and an in-memory foreground lease. The lease expires on backgrounding, screen lock, opening a source app, or five minutes without activity.

Box content uses secure task-window behavior so notification text is not exposed in recent-task previews.

### Settings

Show readiness first, then call/alarm policy, allowed apps, Emergency Access, retention, clear Box, and privacy. Allowed apps cannot change during Focus. Clear Box explains that it removes local snapshots only.

All user-facing strings live in resources. State is expressed through text and icons in addition to color. Layouts support dark theme, landscape, large text, TalkBack, compact phone, tablet, and foldable-sized windows.

## Testing strategy

Use JUnit 4, kotlinx-coroutines-test, Room in-memory instrumented tests, Compose UI tests, UI Automator for system surfaces, and JaCoCo. Do not add a mocking library unless a platform API cannot be replaced by a fake.

Test-first domain coverage includes circular interval validation, cross-midnight schedules, DST gaps and overlaps, Start now extension, continuous-session merging, state reconciliation, idempotent boundaries, notification filtering, key-based upserts, group behavior, retention, permission revocation, and release timeout.

Compose behavior tests cover readiness gates, navigation lockout, Emergency Access relocking, validation errors, confirmation flows, empty/list/error states, state restoration, and source-app failure. Window tests cover compact, medium, and expanded widths, short and tall heights, font scale 1.5, light and dark theme.

Instrumented tests cover Room constraints, service integration, alarms, boot/time broadcasts, notification permission and channel state, Zen rule lifecycle, real notification callbacks, process restart, and end-to-end Focus release.

The automated emulator matrix targets API 33, 34, 35, and the latest stable API available during development. AOSP/Google emulator results prove framework-level behavior only. At least one real OEM device is required before claiming OEM compatibility. Sound, vibration, Heads-up, status-bar flash, calls, alarms, navigation, media, OEM power management, and reboot behavior require guided human observation where Android exposes no trustworthy assertion API.

## Compatibility gate

A device/ROM/OS tuple passes only when:

- All eligible notifications are captured once and cause no perceptible Focus-time alert.
- Notification updates change the snapshot without increasing distinct count.
- Original notifications restore silently.
- Exactly one nonoti summary alerts after the Zen rule is removed.
- Permission loss, restart, reconnect, clock change, and release timeout cannot leave persistent DND, false Focus, duplicate data, duplicate summaries, or permanently lost notifications.
- Unsupported behavior prevents Focus instead of silently degrading.

The app can be built and tested without completing the real-device matrix, but it must not claim universal Android compatibility until the matrix passes. The in-app compatibility gate preserves that boundary.

## Explicit exclusions

No internet permission, account, backend, cloud sync, analytics, ads, crash upload, AI, auto-reply, accessibility service, app blocking, work-profile support, multi-user support, remote notification actions, or notification recreation is included in v0.1.0.
